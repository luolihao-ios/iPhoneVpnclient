# HTTP 204 节点可用性检测设计

## 背景

当前 Windows 节点检测在本地 sing-box HTTP 代理返回 `CONNECT 200` 后，立即把节点标记为可用。该响应只能证明本地代理接受了隧道请求，不能保证节点已经成功连接外部网络，因此坏节点也可能被误判为可用。

本次检测调整为常见代理客户端使用的轻量 URL Test：通过待测节点访问 `http://www.gstatic.com/generate_204`。只有实际收到 HTTP 204，节点才算可用。

该地址已在当前 Windows 网络环境实测：首轮约 405 ms，后续稳定约 61–63 ms；明显快于 Cloudflare HTTP 204，且没有 YouTube 检测的超时问题。

## 目标

- 检测所有订阅节点，不因已找到若干可用节点而提前结束。
- 每个 Windows 节点从启动临时核心到完成验证共用 3 秒总时限。
- 只有流量真实经过待测节点并收到 HTTP 204 时，才标记为可用。
- 不下载完整网页，不查询出口 IP。
- 用完成 HTTP 204 请求的总耗时作为节点延迟。
- 保留现有取消检查、并发控制和结果排序行为。

## 检测流程

1. 为待测节点生成独立 sing-box 配置并启动临时核心。
2. 等待临时本地 HTTP 代理端口开始监听。
3. 通过该本地代理请求 `http://www.gstatic.com/generate_204`。
4. 请求必须走待测节点的全局出站，不允许回落到直连。
5. 收到 HTTP 204 后立即结束，不读取网页正文，并将节点标记为可用。
6. 收到其他状态码、连接失败或总时限用尽时，将节点标记为不可用。
7. 从启动临时核心到收到响应共用一个 3 秒总时限，请求阶段不会重新获得完整 3 秒。
8. 无论成功或失败，都停止临时核心并删除临时配置文件。

## 判定规则

- 可用：通过待测节点收到 HTTP 状态码 204。
- 不可用：没有收到 204，包括仅收到本地 `CONNECT 200` 的情况。
- 延迟：从开始创建该节点的检测环境到收到 204 的总耗时，最小显示为 1 ms。
- 取消：用户停止检查后，不再领取新的节点任务；已完成结果保留，未完成节点恢复为未检查状态。

## 与 FlClash 的关系

FlClash 将延迟测试交给 ClashMeta/Mihomo 的 URL Test，通过节点访问 `generate_204` 地址。绿色延迟表示测试 URL 已经通过该节点成功响应，而不是普通 ICMP Ping。本设计采用相同的判定思路，但在 Forge VPN 中继续使用独立 sing-box 进程隔离每个节点。

## 错误与日志

- 日志记录测试目标、超时、返回状态码和精简后的异常信息。
- 用户界面继续只显示“是/否”、延迟和检查状态，避免暴露过长的底层错误。
- 单个节点失败不得中断其他节点检测。

## 测试

- HTTP 204 响应判定为可用。
- 仅收到本地 `CONNECT 200`，但没有收到 204，不得判定为可用。
- HTTP 200、301、403、5xx 和空响应均判定为不可用。
- 请求与临时核心启动共享 3 秒总预算。
- 全节点筛查不会因已获得可用节点而提前停止。
- 现有停止检查、Windows 代理恢复和构建测试继续通过。

## 非目标

- 不判断出口 IP 所属国家或地区。
- 不测试下载速度、视频播放、TLS 性能或完整网页加载。
- 不改变移动端现有的 TCP 检测实现。
- 不调整订阅解析、节点协议配置或系统代理管理逻辑。
