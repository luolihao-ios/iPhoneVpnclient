# 三组 DoH 自动切换设计

## 背景

2026 年 8 月 12 日的 iPhone 日志表明，VPN 隧道和代理节点能够建立连接，但本地 DNS `223.5.5.5` 给部分海外域名返回了错误地址。流量随后虽然进入代理出站，却连接到了被污染的目标地址，因此出现“VPN 显示已连接，但所有需要代理的网站都打不开”的现象。更换节点和订阅不能解决这一问题，因为故障发生在域名解析阶段。

此前使用单个 Cloudflare DoT（TCP 853）时，部分 AnyTLS 节点又会超时。此次改为通过当前代理节点访问 DoH（HTTPS 443），并内置三组解析器，在单组不可用时自动切换。

sing-box 1.13.14 的 `dns.final` 只能指定一个 DNS 服务器标签，不支持填写服务器列表后自动回退。因此，三组切换由 Forge VPN 的连接控制层完成，sing-box 每次连接只激活其中一组远程 DoH。

## 目标

- 内置 Cloudflare、Google、Quad9 三组远程 DoH，不要求用户填写地址。
- 海外域名不再交给本地 DNS 解析，避免 DNS 污染。
- 当前 DoH 无法完成真实联网验证时，自动切换下一组并重连。
- 优先复用上次验证成功的 DoH，减少正常连接耗时。
- 三组全部失败时停止 VPN，不允许界面继续显示“已连接”。
- iOS、Android 和桌面端共用同一套 DNS 配置生成逻辑。
- 日志能够明确显示当前解析器、切换原因和最终结果。

## 非目标

- 不允许用户编辑或导入自定义 DNS；本次只实现三组内置解析器。
- 不做常驻后台的周期性测速，也不持续轮询 DNS。
- 不根据国家、运营商或网络类型维护更多解析器名单。
- 不改变订阅解析、节点协议和中国规则集的来源。
- 不把节点不可达与 DNS 故障精确归类；联网验证失败时只按有限次数尝试其他 DoH。

## 内置解析器

三组解析器顺序固定，但首次尝试从“上次成功项”开始：

1. Cloudflare：`1.1.1.1:443`，TLS Server Name 为 `cloudflare-dns.com`，路径 `/dns-query`。
2. Google：`8.8.8.8:443`，TLS Server Name 为 `dns.google`，路径 `/dns-query`。
3. Quad9：`9.9.9.9:443`，TLS Server Name 为 `dns.quad9.net`，路径 `/dns-query`。

服务器使用 IP 地址连接，避免解析 DoH 服务自身域名造成启动循环；TLS 仍使用对应域名校验证书。三组服务器均设置 `detour: proxy`，保证 DoH 请求经过当前代理节点，而不是从本地网络直接访问。

## DNS 配置规则

共享配置生成器接收一个明确的 `remoteDnsProvider` 参数，并生成本地 DNS 与三组 DoH 服务器。`dns.final` 每次只指向当前选中的远程 DoH 标签。

不同路由模式采用以下规则：

- 智能分流：节点服务器域名走本地 DNS；中国域名规则集走本地 DNS；其余域名走当前远程 DoH。中国域名和中国 IP 的路由规则继续直连，其他流量走代理。
- 全局代理：仅节点服务器域名走本地 DNS；其他域名全部走当前远程 DoH；除现有必要直连项外，业务流量走代理。
- 直连模式：继续以本地 DNS 为最终解析器，不启动远程 DoH 自动切换。

节点服务器域名必须始终由本地 DNS 解析，否则在代理节点尚未建立时，DoH 又依赖代理节点，会形成循环依赖。

现有把 `1.1.1.1` 强制直连的路由例外需要收窄，不能覆盖内置 DoH 的代理拨号。应用硬编码的普通 UDP 53 请求仍由 DNS 劫持规则接管，不允许借此绕过当前解析策略。

## 自动切换流程

连接控制层维护本次连接的尝试序列。默认顺序为 Cloudflare、Google、Quad9；若本地保存了上次成功项，则从该项开始，再循环尝试其余两项。例如上次成功的是 Google，本次顺序为 Google、Quad9、Cloudflare。

每次尝试执行以下步骤：

1. 使用当前 DoH 生成 sing-box 配置，并在日志写入解析器名称和序号。
2. 启动 VPN，等待平台报告隧道已连接。
3. 通过当前运行中的代理出站请求 `http://www.gstatic.com/generate_204`，验证 DNS、代理出站和外网连通性组成的完整链路。移动端使用普通网络请求，使流量进入系统 TUN；桌面端显式通过当前 sing-box 的本地 HTTP 代理发送请求，禁止用本机直连结果代替。
4. 收到预期的 HTTP 204 后，将当前 DoH 记为上次成功项，连接流程结束。
5. 超时、解析失败、连接失败或返回非 204 时，停止本次 VPN，记录简短原因，然后自动尝试下一组 DoH。
6. 三组均失败后停止 VPN，将运行状态设为未连接，并向用户显示“三组远程 DNS/代理链路均不可用，请检查节点或网络”。

单次用户连接最多尝试三组，每组只尝试一次，不允许形成无限重连。每组在平台报告已连接后获得 5 秒的 HTTP 204 验证时限；平台自身的隧道启动仍沿用现有超时机制。用户主动断开、切换节点或再次点击连接时，立即取消尚未完成的自动切换流程，过期结果不得覆盖新连接状态。

自动切换只发生在连接建立阶段。连接成功后不进行后台周期轮询，以避免额外耗电、流量和网络抖动。用户重新连接或执行现有的 VPN 检查时，可以重新触发验证。

## 状态持久化

使用稳定的解析器标识保存上次成功项，而不是保存数组下标，避免以后调整列表顺序造成错配。建议键名为 `remote_dns_provider`，值限定为：

- `cloudflare`
- `google`
- `quad9`

只有完整链路验证成功后才更新该值。三组全部失败、用户主动取消或应用异常退出时，保留原有成功记录。

## 组件边界

### DNS 提供器模型

负责描述稳定标识、显示名称、服务器 IP、端口、TLS Server Name 和 DoH 路径。该模型不负责连接和持久化。

### sing-box 配置生成器

负责根据路由模式与当前 DNS 提供器生成确定性的配置。相同输入必须产生相同 DNS 和路由规则，便于纯单元测试。

### 连接尝试协调器

负责排列三组尝试顺序、控制每次启动与停止、执行联网验证、取消过期尝试并返回最终结果。它不解析订阅，也不直接操作界面。

### 平台连接适配层

iOS、Android 和桌面端继续使用各自现有的启动/停止方式。协调器只依赖统一的“启动、等待连接、验证、停止”接口，平台差异不得泄漏到 DNS 配置模型中。

## 日志与用户提示

日志至少包含：

- `[dns-fallback] attempt=1/3 provider=Cloudflare`
- `[dns-fallback] provider=Cloudflare result=failed reason=...`
- `[dns-fallback] switching Cloudflare -> Google`
- `[dns-fallback] provider=Google result=passed status=204`
- `[dns-fallback] all providers failed`

失败原因需要去除完整订阅、密码、UUID、节点密钥和 URL 查询参数。界面只显示简洁中文结果，详细原因保留在可导出的日志中。

## 错误处理

- VPN 启动失败：停止当前尝试并切换下一组。
- 已连接但 204 验证超时或返回错误状态：停止当前尝试并切换下一组。
- 验证请求必须实际经过当前 VPN/代理；不能因设备本身能够直连验证地址而判定代理成功。
- 用户主动断开或更换节点：取消整个尝试序列，不再自动重连。
- 应用收到旧尝试的迟到回调：根据连接代次丢弃，不修改当前状态。
- 三组全部失败：确保系统 VPN 已停止，并返回单一、可理解的错误。
- 直连模式：不执行远程 DoH 回退，避免把普通直连网络故障误判为代理 DNS 故障。

## 测试范围

### 配置单元测试

- 三组 DoH 的 IP、443 端口、TLS Server Name、路径和 `detour: proxy` 正确。
- 智能分流下，中国域名走本地 DNS，海外域名的最终解析器为当前 DoH。
- 全局代理下，除节点域名外最终解析器为当前 DoH。
- 直连模式仍使用本地 DNS。
- 节点服务器为域名时始终存在本地 DNS 规则；节点服务器为 IP 时不生成多余域名规则。
- 内置 DoH 地址不会被普通强制直连规则截获。

### 协调器单元测试

- 没有历史记录时按 Cloudflare、Google、Quad9 尝试。
- 有历史记录时从上次成功项开始循环。
- 第一组成功后不再尝试其余两组，并保存成功项。
- 第一组失败、第二组成功时，先停止第一组再启动第二组。
- 三组全部失败时停止 VPN、保持未连接并返回最终错误。
- 用户取消后不会继续切换，迟到回调不会覆盖新状态。
- 非 204 响应不能判定成功。

### 集成与真机验证

- iPhone 智能分流：国内应用直连，Google/YouTube 等海外服务可访问。
- iPhone 全局代理：海外服务可访问，日志显示远程 DoH 经代理使用。
- 人为让第一组 DoH 失败后，应用自动切到第二组并成功连接。
- 三组全部不可用时，界面不显示假连接。
- Android 和 Windows 使用相同配置规则，不发生 DNS 回退逻辑差异。

Flutter 构建和真机安装仍由用户执行；代码提交时提供需要运行的精确测试命令和真机验收步骤。
